# Durable runs

A run can outlive a context window, a crash, or the person going away. The event log is the run, and memory is only a cache of it.

## State

- `.coordinator/runs/<run>/events.jsonl` is the run: one event per change, append only. `state.json` beside it is a snapshot derived from the events (goal, bar, fence, budget, units, rounds, notes and decisions), which every reader uses.
- State written by an older version still loads: fields added later (a round's `cause`, behaviours, evidence, a unit's log and links) are optional. A `state.json` with no `events.jsonl` (0.5 and older) loads as it is; its first change writes a `run.imported` event holding it, then the change.
- Every write happens behind the run's lock file and is atomic (a temporary file renamed over the real one): the event first, then the snapshot. Two writers cannot corrupt the run; a lock older than 30 s is taken over.
- `.coordinator/runs/<run>/workbench.md`, `hud.html` and `units/<unit>.html` are rewritten after every change, inside the same lock. Evidence files live in `artifacts/<unit>/` beside them. An evidence item's `file` is always `<unit or _goal>/E<n>-<name>`: the event schema refuses any other value (on write, `pull` and replay, and in a hand-edited `state.json`), and every read goes through `storedPath` (`lib/evidence.mjs`), which follows no link, refuses a file with a second name (a hard link) and must land directly in `artifacts/<unit>/`; the file is then opened once (no-follow where the platform has it), its handle checked again, and read from that handle. People read them from anywhere, so nobody has to interrupt the loop to ask how it's going (`hud.md`).
- Add `.coordinator/` to `.gitignore`. It is working state, not a deliverable.
- **Artifacts outlive worktrees.** A file a run only mentions by path (a screenshot, a PDF, a log, a JSON or Markdown report in a worktree or a scratch folder) is lost when that folder is deleted. Builders and critics pass what they produce with `run.mjs evidence … --file`, which copies it into `artifacts/<unit>/` with its sha256. Before closing a run, and before removing a worktree, the lead runs `S/run.mjs adopt <run>` (`--dry-run` to preview): it finds every path the run's text mentions outside the run folder and copies each one that still exists, through the same checks as `--file`, as evidence of the unit that mentions it (run-level mentions go to the goal's evidence, `artifacts/_goal/`). The text stays as written; the stored copy is what the dashboard shows. It prints each path as adopted, already (adopted before), repaired (the stored copy was missing or changed, so it was copied again from its source), inside (the run folder), tracked (in the project's git, which keeps it), missing (already gone), unclear (spaces or brackets and not found: quote paths, or attach them with `--file`) or refused, and a second run changes nothing. Quoted paths are read whole; an unquoted path with spaces or brackets is found when it names an existing file, and is called unclear only when it starts with a drive letter or ~ or its folder exists (prose such as "/map 500 without reason; … (map.json" is ignored). It copies only from the allowed roots: the project, its git worktrees, the OS temp folder and the state folder, never a root that is the home folder or holds it. A hard link outside the project is refused. PDFs adopted as kind log by an earlier version are re-tagged pdf. Refused: anything else ("outside allowed roots"), the home folder's configuration (any dot-folder or dot-file at the home root, such as `~/.claude`, `~/.ssh`, `~/.aws`, `~/.docker`, `~/.config`, and `AppData/Roaming`), anything in `node_modules` or `.git`, secret-looking names (`.env*`, `*.pem`, `*.key`, `credentials`, `secret`), symbolic links or paths reached through one, files over the per-file cap (5 MB, text 512 KB) or the 50 MB per run. Types: png, jpg, webp, gif, pdf, txt, log, md, json; text is masked for secrets. `close` warns while mentioned files are not adopted. A stored copy that is missing shows as "missing" on the dashboard (and the live server answers 404), never as a broken image, and `doctor` fails a stored copy that is missing or whose sha256 no longer matches, with the fix: `adopt` again while the source exists, else re-run the step that made it and attach it with `evidence --file`. `pull` does not restore artifacts: evidence files never go to the state branch.

### The event log

Each line of `events.jsonl` is one compact JSON object, keys in this order:

```json
{"v":1,"seq":7,"at":"2026-11-06T10:41:07.120Z","kind":"unit.beat","unit":"u1","payload":{"ops":[{"op":"set","path":["units",0,"heartbeatAt"],"value":"2026-11-06T10:41:07.118Z"}]}}
```

- `v`: schema version, 1. `seq`: 1, 2, 3 … with no gap. `at`: ISO time, UTC. `kind`: what happened. `unit`: the unit it concerns, when there is one.
- `payload.ops`: the change, as the smallest list of `set` (path, value), `del` (path) and `push` (path, values: a list grew). A path is object keys, plus, inside a list, either `{ "id": "u1" }` for lists of records with ids (units, behaviours, evidence) or an index for lists without (notes, rounds, a unit's log). So `unit.add` is one `push` to `units` carrying the whole unit, and a later change reads `["units", {"id": "u1"}, "status"]`: each event makes sense on its own, and no event depends on where a unit sits in the list. Replaying every event's ops from nothing gives the snapshot exactly. `run.imported` carries `payload.state` (the whole old state) instead; `run.init`'s single op sets the whole state.
- Kinds: `run.imported`, `run.init`, `run.freeze`, `run.integrate`, `run.stop` (`next` recorded stops), `run.close`, `run.pause`, `run.resume`, `lead.claim` (a window claimed the run, took it over, or, as its lead, recorded its window's process again: One lead, below), `unit.add`, `unit.start`, `unit.beat`, `unit.built`, `unit.reset`, `unit.verdict`, `unit.strategy`, `unit.detect`, `unit.link` (also a `--continues` link, on both runs), `unit.extend`, `unit.ship` (`ship`: merged on the person's decision without a final verdict), `unit.specialist` (`add-specialist`), `unit.touches`, `unit.sync`, `unit.foldin`, `behaviour`, `evidence`, `note`, `study`, `question`, `answer`, `answer.used`, and `state.edited` (below). `unit` is required for the `unit.*` kinds, optional for behaviour, evidence, note, question and the answers, absent otherwise.
- Every kind has a JSON Schema (`scripts/lib/eventschema.mjs`, `schemaFor(kind)`). Each event is checked when written and every line when read. A torn last line, a line that is not JSON, an unknown kind, a broken schema, or a `seq` that skips or repeats fails loudly, naming the line; nothing is guessed. Paths never contain `__proto__`, `constructor` or `prototype`. Every string anywhere in an event is at most 64 KiB (`MAX_TEXT`); `run.mjs` keeps its own text far shorter, so only a hand-edited or hostile log meets the cap.
- A step that changes nothing (`show`, `next` with no stop) writes no event.

### The snapshot

`state.json` is the state in canonical form, on one line: keys sorted, lists in the order things happened (units in the order they were planned, so a stacked unit follows its base, as `next` and the dashboard list them), plus:

```json
"snapshot": { "v": 1, "seq": 42, "sha256": "<SHA-256 of events.jsonl up to and including line 42>", "stateSha256": "<SHA-256 of the state without this key>" }
```

- On read: the log ahead of the snapshot (a gap), a `sha256` that does not match the log, or an unreadable snapshot means the state is rebuilt from the events. A reader rebuilds in memory; the next write saves the rebuilt snapshot.
- A snapshot that names more events than the log holds, or names events when `events.jsonl` is missing, fails loudly: the log lost events. Restore it with `run.mjs pull`.
- A snapshot whose body no longer matches `stateSha256` was changed outside `run.mjs` (by hand, or by an older version of the scripts). It is kept: the next write first records the difference as a `state.edited` event, so the log still replays to the snapshot.
- The snapshot repeats the text the events hold (goals, notes, evidence). Every reader (`show`, the dashboard, `watch`, `serve`, the coordinator's own page) reads the whole state from it, and a snapshot that pointed into the log would make each of them replay the run. Text is capped where it is written, so the copy stays small.

### Pit stops: the state in the repo

`S/run.mjs push <run>` copies the run to the primary repo so another machine can carry on. The lead calls it at **pit stops only**: a unit merged, a decision recorded, the run closed. Never on every event: the local log is the working copy between pit stops, and the repo's history stays one commit per pit stop.

- Where: an orphan branch, `coordinator-state` by default (`--to <branch>`), never `main`, `master` or the remote's default branch, and never a branch that does not already hold coordinator state. `--to ./folder` (or an absolute path) writes a folder instead. The commit is pushed to the repo's `origin` with a normal (non-force) push, retried on a race; pre-push hooks run, and one that fails fails the push with its message (the commit is built with `git commit-tree`, so pre-commit and commit-msg hooks do not run). A repo with no remote only gets the local branch. Nothing is checked out.
- Only forward: a push refuses, and changes nothing, unless the copy's `events.jsonl` for the run is a prefix of this machine's (masked) log, or differs from it only by answers and person notes this machine has already replayed (below). A copy with events this machine lacks needs a `pull` first; two machines that both added events after the same point stop with "different histories after event N", the same words `pull` uses. To recover from different histories: move the local run folder (`.coordinator/runs/<run>`) aside, `run.mjs pull <run>`, then redo the local changes on top; both errors say so.
- What: `runs/<run>/events.jsonl`, `runs/<run>/state.json` (rebuilt from the copied events), `runs/<run>/README.md` (the workbench), `lessons/lessons.json` (project lessons), `stats/runs.jsonl` (one line per closed run: outcome, minutes, units, passed, rounds), and a root `README.md` and `.coordinator-state` marker. Evidence files never go.
- The project map, when a pit stop staged one (`run.mjs map <run> --pit-stop`): `runs/<run>/map/events.jsonl` and `map.md`, under the same forward-only rule, restored by `pull` (`map.md` has the details).
- Masked: every string goes through the secret masking, the project path becomes `.` and the home folder `~`.
- Public repos: run state never goes into a public repo (design Q7). `.coordinator/coordinator.json` says where it may go: `{"visibility": "private" | "internal" | "public", "stateRepo": "<URL or path of a private companion repo>", "remote": "origin", "branch": "coordinator-state"}`, all optional. Without `visibility`, the GitHub CLI is asked; if nobody can tell, the push is refused. A public repo needs `stateRepo`, and then only the companion repo is written.
- Answers and notes from the web dashboard or a `/coordinator` comment command are appended to the copy's `events.jsonl` by the service (the same `answer` / `note` events). After asking a question, push (a pit stop), and `pull` at the next loop step. When the local log is no further than the copy, `pull` fast-forwards onto them. When the lead has logged more since its push (beats, verdicts), the two logs differ after the push, and `pull` replays the copy's extra events on the local log instead: only if every one is an `answer` or a person's `note` (`note --kind person`) and does nothing else; each goes through the same checks and lock as `run.mjs answer` and `note`, in the copy's order, as new local events (seq renumbered, the original time kept). Anything else in the copy's extra events, or an answer or note with fields `run.mjs` never writes, stops with "different histories" and changes nothing; so does an answer that names an option the question lacks. An answer to a question the lead has already used, or closed by a decision, typically changed on the web before the lead's push showed it, does not change it: the lead keeps the used answer or its decision, and the change is recorded as a person's note flagged `changedAfterUse`, which the service alerts on (design 9). Its text says which: "answer changed after use: qN → …" or "answer changed after the lead decided: qN → …". A closed run still takes these: `pull` replays answers and notes on a closed local run too, so a late answer or note is kept on the record (`run.mjs note` and `answer` refuse a closed run; `pull` does not). A second `pull` adds nothing. The next `push` then replaces the copy's log with the local one, which holds every replayed event; a push while the copy still has answers or notes the local log lacks is refused ("pull first"). `lib/incoming.mjs`.
- **Repairing a forged event on the branch.** Anyone with push access can append to the branch's `events.jsonl` by hand. An event that passes the schema but cannot be replayed here, such as a person's note on a unit the run does not have, stops `pull` ("no unit ghost in run r") and so `push` too ("pull first"), and the run cannot move forward. The local log is the good copy; remove the bad event from the branch, then carry on:
  1. `git fetch origin coordinator-state` and `git log -p origin/coordinator-state -- runs/<run>/events.jsonl` to find the commit that appended it, and who made it.
  2. Revert that commit on the branch, from a scratch worktree: `git worktree add ../state-fix origin/coordinator-state`, then in it `git switch -c fix-state`, `git revert <sha>`, `git push origin fix-state:coordinator-state`, and remove the worktree. A plain push, never a force: if the branch moved meanwhile, fetch and repeat.
  3. `run.mjs pull <run>` then says the copy is behind or up to date, and the next `push` writes the run. The hosted service re-reads the branch on that push.
  A forged event that the schema refuses fails `pull` loudly with its line number; the repair is the same. If the event came from someone you did not expect, check who has push access to the state repo.
- `S/run.mjs pull <run> [--from <branch>|./folder]` on another machine restores the run (and the project lessons, if it has none), or appends the copy's newer events to the local log. A local log with events the copy lacks is never overwritten: pull says `local-ahead`, or refuses when the two histories differ.

## Background agents

- Start builders and critics as background agents. The harness notifies the lead when one finishes, so never poll and never sleep-loop.
- Long checks, such as full test suites, builds or visual sweeps, run as background commands that write a log file. The agent reports the log path and the pass or fail line.
- The agent beats with `run.mjs beat <run> <unit>` at each milestone: it pushed, the tests ran, the review finished. The builder and critic briefs carry the exact command. `next` returns `check-stale` for a builder or critic with no beat for `--stale-minutes`.
- **Stale:** first ask the agent for its status. If there's no answer:
  - with `phase: building`, `start` the unit again and send a fresh builder from the last pushed state;
  - with `phase: judging`, the build is kept: `beat` the unit and send a fresh critic.
- **Where the state is:** `.coordinator/` sits beside the main checkout, so builders in git worktrees of the same repo reach it with no setup. An agent working anywhere else (another clone, another machine path) gets `COORDINATOR_DIR=<dir>` in its brief; `S/run.mjs where` prints the value.

## One lead

Each run has one lead window, in whatever tool (`scripts/lib/lead.mjs`; design: `docs/design/one-boss.md` 5.1, 5.2).

- **Claiming.** `init` claims the run for the window that starts it, after checking its `--lead` (a bad one leaves no run); a run made before runs recorded a lead is claimed by its first lead step. The `lead.claim` event records the lead id, the tool and the time, never a host or user name. A lead step writes the claim it needs together with its own change, as two events in one locked write: when the step fails, neither is written.
- **The id.** Where the tool gives each window its own session id, the id is a short hash of it, and the tool's window process (when it gives one) is recorded with a value for this PC: a hash of the PC's random id (made once in the coordinator's home folder), the project's key (a hash of its state folder) and the run's id. Two runs pushed from different repos, even under the same run id, so hold different values, and neither can be tied to the PC. The process is recorded again by each of its lead steps and by its own `run.mjs lead <run>` (a resumed window has a new process). `push` blanks it (`pid: null`): a process id means nothing off this PC, so the copy keeps only the PC's value. So far only Claude Code (`CLAUDE_CODE_SESSION_ID`, `CLAUDE_PID`), the one tool checked. Every other tool passes `--lead <id>` on each lead step or sets `COORDINATOR_LEAD` in that window's shell only (never a profile file, or every window shares one id); without either, the claim makes a random id and prints how to pass it. A tool's variables join the table in `lead.mjs` (`SESSION_VARS`) only once verified, never guessed.
- **Lead steps:** `init`, `add`, `add-specialist`, `start`, `reset`, `verdict`, `strategy`, `extend`, `freeze`, `foldin`, `ship`, `integrate`, `close`, `ask`, `use-answer`, `pause`, `resume`, `push`, `pull`, and `next` when it records a stop (there is no stop command: `next` and `close` record stops). From any other window they are refused, naming the lead's tool and its last activity. Never refused: `beat`, `built`, `evidence` and an agent's `note` (builders and critics keep working whoever leads), read-only steps (`show`, `status-line`, `questions`, `list`, `next` that records nothing), answers and person notes. `pull` checks without claiming, so the local log does not fork from the copy: even `pull --takeover` against a gone lead claims nothing; the next lead step does.
- **Gone.** A lead is gone, and its run can be taken over, in two cases. **Ended:** its tool gave its window's process (Claude Code), that process no longer runs on this PC, and the run saw no lead step of its own and no unit beat for 10 minutes (`ENDED_MINUTES`). A resumed window (same session, new process) keeps its run if it acts within those 10 minutes: its next lead step, or `run.mjs lead <run>`, records the new process. **Quiet:** whatever its process, no lead step and no unit beat for the run's `--stale-minutes` (45 by default). An unknown process (a tool that gives none, or one recorded on another PC) or one that still runs uses only the quiet rule, so a reused process id cannot keep a quiet lead. The takeover says which: "its window has ended and it has been quiet for over 10 min", or "quiet for over N min".
- **Taking over.** `S/run.mjs lead <run>` prints who leads, since when and when last active, and claims the run when it has no lead or its lead is gone; a lead step with `--takeover` does the same for a gone lead. A lead still active is taken over only by `S/run.mjs lead <run> --takeover --reason "…"`, and only after the person says yes: a lead step's `--takeover` never does it, and a step's own `--reason` is never a takeover's reason. Every takeover is logged as a decision: "took over from <id>: <why>". The old window's next lead step is refused, so it stops instead of competing.
- **No second builder.** `start` on a unit being built or judged whose last beat is younger than the stale minutes is refused, with the beat's age; `--takeover --reason "…"` from the window that already leads the run starts it anyway and logs it on the unit. Taking over the run and taking over a unit at work are separate steps: a window that does not lead the run yet takes it over first (`lead`).
- **Linked runs.** `init --continues` and `add --continues` also write the parent run's side of the link, so they are refused while another window actively leads the parent; a gone lead, or none, is fine (nothing is claimed there).
- **Ages come from the script.** `show`, `next`, `status-line`, `lead` and the refusals print each last beat and last activity as minutes ago plus this PC's clock time and zone: "52 min ago (14:05 local, UTC+3)". Never work an age out from a UTC timestamp in the log.

## Resume

After compaction, a restart or a new session:

1. Run `S/run.mjs list`, then `S/run.mjs lead <run>` and `S/run.mjs show <run>`. When another window still leads the run, leave it to that window: take it over only with the person's yes (One lead, above).
2. For each in-progress unit, check its branch, worktree or output for the latest real state. A unit with no artifact goes back to build with `S/run.mjs reset <run> <unit> --reason "…"`, so nobody waits out the stale timer.
3. Run `S/run.mjs next <run>` and carry on.

## Isolation

- Code: one worktree and one branch per builder, created from the current base. Install dependencies in each worktree. Never link `node_modules` or other shared folders between worktrees: deleting one can delete the other.
- Databases or services shared with other work: give each builder its own database or port, recorded in the unit's notes.
- Stacked work, where B builds on A: B branches from A's branch, rebases after A merges, and opens its PR only then (`run.mjs add … --after A`).
