# /coordinator run <task>

**Standing rules, every run.** Read `references/context.md` before the first launch and follow its eight rules for the whole run: a builder is closed when it reports, a fix round goes to a fresh agent (finding list plus diff, `references/briefs.md`), every agent and you keep a context budget, you keep your own context lean (the run state is your memory), every brief is short and complete, one critic per round. The briefs from `S/run.mjs brief` carry them. The retro records the token totals (`references/learning.md`, step 7). They are not optional reading.

## 1. Intake: everything up front

**First, two quick steps that ask nothing:**

- `S/run.mjs dashboard` starts the PC dashboard, or prints its link when one is already up. It keeps running when this window closes, and it takes the answers to every run's questions. Give the person the link once.
- `S/run.mjs waiting` lists what already waits on the person across this PC, oldest first. Mention the items older than a day in one line, at most once per window per day. Do the same when you resume a run (`status.md`).

1. Read `COORDINATOR.md`. If it is missing, do `init`'s reading now and put its questions into this run's single batch (step 7); write the file after the answers. Read the task in full: the issue, its comments, linked issues, the PR and its review state.
2. Load lessons: `S/lessons.mjs list --tag <domain> --top 8` (also `--scope project`).
3. Draft the **goal**, the **bar** (`references/bar.md`), the **fence**, the **units** with their sides (`references/guardrails.md`, Test runs) and the **budget** (`references/guardrails.md`, defaults from `S/run.mjs stats`). For work across several repos or issues, follow `references/sub-skills/plan.md`.
4. **Research now, not mid-run.** For anything people will see, collect references: the person's own (Mobbin, screenshots, a design system) first, then web research (`references/craft.md`). When the project has `.prism/`, its tokens and anchors are the reference. When visual work starts with no `.prism/tokens.json` and the harness lists Prism, ask in the batch whether to lock the look first in a look-dev unit (`references/prism.md`). For unknowns in the code or the domain, send a researcher with `references/sub-skills/investigate.md`. Put what you find into the bar.
5. **Staff the team** from the harness's agents and skills (`references/team.md`), and pick each role's playbook (`references/sub-skills.md`).
6. List every question whose answer would change what gets built or what you may do:
   - **the goal, made specific for the kind of task.** A vague goal gives a vague bar, and the run then builds the wrong thing well.
     - New work or a new project: ask what the person expects at the end: who it is for, what it must do first, what "done" looks like to them, and what is out of scope.
     - Bug fix, feature or refactor: find the specific goal yourself first, in the task, the issue and its comments, the code and the person's own words. For a bug that is the wrong behaviour and the right one; for a feature, what a person can do afterwards that they cannot do now; for a refactor, what must not change and what gets simpler. Ask only for what is still missing or unclear, and offer the goal you found as the recommended option.
   - open product decisions, unclear acceptance, scope edges;
   - every "needs a person" action this run will reach (merge, push, migration, message);
   - whether the run may open issues or PRs upstream for skill improvements (`references/upstream.md`).

   Infer what you can first.
7. **Ask them all in one batch, through the harness's question tool** (AskUserQuestion in Claude Code), never as prose in the reply:
   - each question opens with a tiny context line, so it can be answered cold. The run does not exist yet, so there is no label from `run.mjs ask`: use the same shape, `<project> · <run id> (new run) · <what it decides>`;
   - **each question stands on its own, in plain English:** the real-world situation in everyday words, why it matters to the person, and each option as its plain consequence ("each server sends its own notice: with three servers you may get three"). No run jargon: no unit ids, rounds, cause tags, behaviour ids or scores without saying what they mean. The test: could someone who has not followed the run answer it? This holds for every question, here and mid-run;
   - your recommended option comes first, marked as recommended;
   - put the draft goal, bar, fence, references and staffing in the reply just before the call, and make "Is this draft right?" one of the questions;
   - the tool takes a few questions per call (four in Claude Code): send the rest in the next call, straight away;
   - when `.coordinator/coordinator.json` sets no `"asking"`, include "How should I ask you during the run?": **the dialog** (recommended: you answer in this terminal, and this window waits for you) or **dashboard first** (I write each question here and on the dashboards and keep working; answer in either place). See Asking, below.

   With no question tool, send one numbered list: each question with its options, the recommended one first. Only you ask. Builders, critics and integrators report questions and blockers to you.
8. Keep every answer: right after `init` (step 2) each one is recorded with `S/run.mjs note <run> --kind decision --text "…"`; the asking answer also with `--asking dialog|dashboard`. Approvals for gated actions are recorded the same way and cover this run only.

From here the run is **unattended**. Do not ask the person anything until the report, except the questions step 3 names: `ask-person`, a gated action, a design change, the round-3 value question and a second quiet agent in one round. What you do without asking is in `references/guardrails.md` (Without asking, and what still asks).

## 2. Set up

`S/run.mjs init <run> --tag <domain> --goal … --bar … --fence "<scope in words>" --paths <dir,dir> [--repo owner/name] [--theme <design-system.css>]`, then `add` each unit (`--after` for stacked work; `--title "#1206 Security gaps"`, `--issue owner/repo#1206` and later `--pr`, repeatable for linked repos, so the dashboard names and links it; one `--behaviour "Given … when … then …"` per behaviour of its bar, `references/bar.md`, optional `--statechart <path|json>`), then `freeze [--statechart …] [--skip-feasibility]`. Give the goal its own behaviours with `behave <run> --goal --text …`. Then record the intake answers (step 1.8) on the run. `--paths` is the fence as path prefixes; the detector reads it. Give each unit its own `add … --paths <dir,file>` too: a unit whose paths overlap a unit being built waits (`next` says `paths overlap …`), and units with separate paths build at once, in their own worktrees. With several runs, `next --all` gives the actions of every open run this window leads. Small follow-ups are triaged as they come, never a unit each: `followup <run> --text … --triage batch|P1|P2|P3|drop --reason …`; batch items make one `batch` unit that builds last, P1 and P2 are filed as issues. Every change also rewrites the run's snapshot, `hud.html` (`references/hud.md`).

**You are the run's one lead.** `init` claims the run for this window. Only the lead runs lead steps: the steps that change the plan or the run's course (`add`, `start`, `verdict`, `ask`, `use-answer`, `close`, `push`, `note --asking` and the others in `references/durability.md`, One lead). Builders and critics keep working whoever leads. Claude Code gives each window its own id, so there is nothing to pass. In any other tool, `init` prints a lead id: pass it on every lead step as `--lead <id>`, or set `COORDINATOR_LEAD=<id>` in this window's shell only (never in a profile file, or every window shares it). Note it beside `S`, so every lead step carries it. A lead step refused with "led by another window" means another window leads this run, and "lead is gone" that its lead stopped: either way, stop and follow `status.md`.

**Before `freeze`, check the bar can be met.** Read each behaviour and ask: can this be met at all? Rewrite an "exactly once" or "never" claim across parties that share no state while a dependency is down per party, with the duplicate stated (`references/bar.md`, Can it be met at all?). A critic can be right while the bar is wrong, and no number of rounds fixes that.

**Hear the person at once.** Start two background commands and keep them running until the finish:

- `S/run.mjs watch <run> [--remote]`: one line per new or changed answer and per note from the person. Run it where its lines wake you (a Monitor in Claude Code; elsewhere a background command whose output you check after each agent report). On a line: read it with `S/run.mjs questions <run>` or `show`, act on it, then `S/run.mjs use-answer <run> qN`. A note from the person is their word on the run: follow it inside the fence and the approvals, log scope changes as usual.
  When the run's state is pushed (`push`), add `--remote`: it also pulls the run every 30 s (`--every 10-60`), so answers and notes made on the web HUD or by comment commands arrive within a minute, and within seconds when the coordinator service's doorbell is set (`COORDINATOR_SERVICE`, or `"service"` in `.coordinator/coordinator.json`; it uses your `gh` login). Lines starting `remote:` report the link (doorbell on, pull failed), not answers: no action unless pulls keep failing.
- `S/run.mjs serve <run>`: the live dashboard on 127.0.0.1, with answer forms and a page per unit. Give the person the URL it prints, once. It holds a token: don't paste it anywhere else (`references/guardrails.md`).

## 3. Loop

Repeat `S/run.mjs next <run>` and act on each unit:

When the person stops for a while (overnight, a restart), `S/run.mjs pause <run> --reason "…"`, and `resume <run>` when they say to go on: the clock stops in between, and `next` says `paused` and starts no unit (`references/guardrails.md`, Budget).

| Action | Do |
|---|---|
| `build` | `start`, then send a builder (`references/briefs.md`, playbook `sub-skills/fix.md`) in the background. On its report: `built --report "<its summary>"`; once its PR is open, `link <run> <unit> --pr …`. The builder is then closed. A later `build` of the same unit (a fix round) goes to a new agent with the findings and the diff range, never back to the old one (`references/context.md`, rule 1). |
| `judge` | Code: run `S/detect.mjs --run <run> --unit <unit> --base <base> --head <the builder's commit>` first (it records which commits it checked, and refuses an empty diff). A hit is a FAIL with that gap, unless the change is legitimate (e.g. an intended snapshot update): then rerun with `--allow <rule>:<path>` (repeat it, or comma-separate, for several; the critic's rerun on the same base and head keeps them) and record why with `note --kind decision --unit <unit>`. On a run with `--paths`, a PASS is refused without a clean result for this round. Run the full suite on that head with `S/run.mjs suite <run> <unit> --head <sha> -- <test command>` (one at a time per machine, recorded; the critic's brief then quotes it), and typecheck and lint as shell commands (`guardrails.md`, Test runs). When `next` gives `critics: 1` (round 2 on, a delta under 200 lines), send only that critic (`context.md`, rule 3). Otherwise send one critic (playbook `sub-skills/review.md`, at full depth), plus a specialist critic for a risk area, which must also pass. Pick the critic's model with `S/run.mjs models <run> <unit> --role critic --class <the unit's task classes>` and record it on the verdict with `--model` and the same `--class` (`routing.md`, The cheaper critic). For screens, send the visual critic (`visual.md`) once, after the code critic has passed, not on every round. On a project with `.prism/`, add the specialist `prism` to each visual unit: it passes only on the gate's PASS report for that build, and a FAIL report blocks every pass (`references/prism.md`). Record with `verdict` (adding `--reins-packet <packet.json>` when inspecting a paired app so undeclared `reins_state` transitions fail automatically), copying the critic's `SCORE`, `GAP` and `CAUSE` into `--score`, `--gap` and `--cause` (score and gap are required on a fail) and each BEHAVIOURS line into `--behaviour B1=pass:"…"`; a pass is refused while a behaviour is failing or unchecked. Add `--critic "<setup>"` (who judged, at what depth) so `stats` can compare escape rates per setup. A specialist critic's reply goes in first with `--specialist <name>`; the general pass is refused until every specialist the unit was added with has marked this build. When a specialist failed it, record the general critic's pass as given: the round closes as failed by that specialist, with its gap, cause and severity, and keeps the general verdict and score (`show`, `stats` and the unit page name the specialist); `next` treats it as any failed round. Never record a general fail the general critic did not give. A unit added without one gets it with `add-specialist <run> <unit> <name> --reason "…"` before its verdict (logged as a decision; required from the build being judged or the next one; refused once the unit passed or stopped, or the time budget is spent). |
| `change-strategy` | Pick a different approach, `strategy --text`, then build. When the step carries a `hint` (the same concurrency or consistency cause twice: a race, a lock, a second writer, data out of sync), weigh it first: one shared writer for that state plus a guard test that fails when another path writes it, not a patch on the next writer the critic names. |
| `check-stale` | Ask the agent. No answer and `phase: building`: `start` again and send a fresh builder. `phase: judging`: `beat` and send a fresh critic (the build is kept). Do this without asking once per unit per round; when the same unit goes quiet again in the same round, ask the person (`guardrails.md`, Without asking). |
| `wait` | Nothing. A notification will come; never poll. Each wake-up re-reads your whole context, so when several agents are out, act once the due notices have arrived and read them together (`references/context.md`, rule 5). With `waiting for specialist marks: …`, record each specialist's verdict on the failed round first; only when one cannot come, `start <run> <unit> --force-start --reason "…"` (recorded: its findings on that round are lost). |
| `wait` (`after …`), work started early | When the person asks for a stacked unit to start before its base passed: `beat <run> <unit> --text "…"` logs its progress (marked early; the unit stays open), and a critic's look at it goes in with `verdict <run> <unit> pass\|fail --early --score N --evidence "…"` (`--gap` and `--severity` on a fail, `--specialist <name>` for a specialist, `--head <sha>`). An early review is never a round: it moves nothing and passes nothing, and `next`, `show` and the unit page list it apart (`early`). Once `next` says `build`, `start` begins the first try as usual. |
| any, with `sync` | Another unit that changes the same files merged first. Merge the target into this unit's branch before the review (or before merging, on a passed unit), check the shared files, then `sync <run> <unit>` (`references/briefs.md`, Hot spots). |
| `stop` | Recorded by `next` just now; with `recorded: false` the time budget is spent and nothing was recorded: run the `spent.step` it gives (`close`), which records these stops (`references/guardrails.md`, Budget). Its gap goes in the report. A reason "no progress: only B2 kept failing …" means the rest passed: narrow B2 to a closed list or move it to a unit of its own (`references/bar.md`). |
| `fold-in` | The pass carries fold-ins (`verdict pass --fold`). Have the builder fold them in on top of the reviewed head, run `S/detect.mjs --run <run> --unit <unit> --base <reviewed head> --head <fold head>`, check only those lines and the tests they touch (you, or a light check, never a new critic round), then `foldin <run> <unit> --head <sha> --evidence "…"`. It refuses a head off the reviewed history, a fold over the size caps, or one detect flagged: those need a new round. |
| `ask-person` | **Same behaviour** (reason `same-behaviour: B1`): the same behaviour failed in the unit's two latest failing rounds; same question, options and handling as Same files below (`bar.md`). **Finish line:** every other unit is decided and this one failed from round 2 on (or at 8 or more) with medium findings at most, from every critic. Run the `step` it gives (`ask <run> --finish <unit>`) and ask the same question at once (Asking, below). Record their pick with `answer <run> qN --choice "<label>" --by person --confirm "<their words>"` (or they answer on the dashboard); words that refuse or hedge ("no, do not ship") do not count. `next` then ships it (shown as "Shipped with follow-ups (score N)", every open finding a follow-up in Gaps), records one more round like `extend` (the same-gap and no-progress rules still apply), or stops it. **Same files** (reason `same-files: <file>`): the unit's two latest failing rounds both have high or medium findings in that file. It comes after the stuck and no-progress checks (`lib/rules.mjs`), which stop the unit first. Different words, the same lines: run the `step` it gives (`ask <run> --finish <unit>`), which logs the ready-made question with its options (Change the bar, Simplify the design, Accept as is, One more round), and ask the same question at once (Asking, below), in plain English (step 1.7). Record the pick with `answer`; `next` then ships the unit on "Accept as is" (every open finding a follow-up) or records one more round like `extend` on any other pick. After "Change the bar", rewrite the bar with `behave` first; after "Simplify the design", agree the simpler design with the person first. Do both before the extra round starts. The clock is paused while the question is open and no unit of the run is building or judging (`guardrails.md`, Budget). |
| `done` / `stopped` | Nothing: the unit passed, or was stopped in an earlier round. With `step: merge`, its fold-ins are checked and it can merge. |

**After each verdict and each merge**, move the board if the project has one (`references/sub-skills/board.md`) and write the situation in one or two plain sentences: `S/run.mjs note <run> --kind situation --text "Security gaps: failed twice on the same route gate; a new approach is next. Roles: being checked."` It heads the HUD. Say what is happening and what comes next, in the person's words, not unit ids alone.

**A unit the rules stopped.** Two ways on, both the person's call:
- **More rounds in this run** (a round-budget stop only), only on the person's explicit yes (`lib/approval.mjs`). Ask with an approving option: `S/run.mjs ask <run> --unit <unit> --question "The <title of the unit> step has used its tries. Give it one more try?" --header <unit> --option "Yes|one more round" --option "No|leave it stopped" --approves Yes`. The question must name the unit (`--unit`). Once they pick Yes, `S/run.mjs extend <run> <unit> --reason "…" --answer qN`. One approval is good for one `extend`, given after the unit's last verdict; it gives one round unless their own words or the option name more (`--rounds 2` needs "two more"), and the decision says which. Without `--answer`, their latest note on the unit since its last verdict must say "approve" or "approved" with no no, not, but, if, maybe or question. "No", free text, a hedge or a lead's own answer is refused. The decision note quotes what they approved. Units stopped as blocked by it stay stopped.
  - **The lead may** use an answer or note the person gave on the dashboard (`serve`) or the web (service, comment commands; it arrives by `pull`), or type their words on the CLI when they gave them in the conversation: `answer <run> qN --choice Yes --by person --confirm "<their words, verbatim>"`, `note <run> --kind person --unit <unit> --text "<their words>" --confirm`.
  - **The lead may not** use `--confirm` without the person's own words, paraphrase them into a yes, answer or note for them otherwise (a plain `answer` or `note --kind person` from the CLI never approves), or approve an extension itself. Editing state.json never approves: an answer, note or question (its text, header, options, approving option or stored minutes) last written by a hand edit (`state.edited` in the log) is refused. This guards against mistakes and casual edits, not a determined lead: a forged events.jsonl line cannot be fully prevented on this machine, because the lead holds the files and the dashboard's token too. An approval that matters is best given on the web (the service writes it with the person's own GitHub login) and checked there.
**A unit merged on the person's decision with no final verdict** (they said "merge it" while it was open, building or being judged, or after a stop): `S/run.mjs ship <run> <unit> --merge <PR or merge URL> --reason "…" --confirm "<their words, verbatim>"` (or `--answer qN`, a question on the unit they answered with its approving option or "Ship with follow-ups"; or their latest note on the unit). Their words must not refuse or hedge; the rules for `--confirm` are the ones above. It ends the unit shipped ("Shipped without a final verdict", delivered in the status line and report, never a clean pass in `stats`), links the merge, and files the missing verdict and every open finding of its last round as follow-ups in Gaps. `close` then works as usual: `--outcome done` after the integration check passes. Never `reset` a merged unit to get past `close`.
- **More time for the run** (near or past its time budget), only on the person's approving answer (`lib/approval.mjs`). Ask on the run with the amount stored: `S/run.mjs ask <run> --question "The run has used its time. Give it 60 more minutes?" --header time --option "Yes" --option "No|close it" --approves Yes --grant-minutes 60` (no `--unit`; 1-1440 minutes). The approving option then reads "60 more minutes"; a description you give must say that. The ask is refused, and records nothing, when the question, the header or any option's label or description names another amount (below). Once they pick Yes, `S/run.mjs extend <run> --reason "…" --answer qN`: it adds exactly the stored minutes (`--minutes M` for fewer, never more) and logs a decision quoting their words and the amount. Minutes are never read from text: `extend` is refused for a question without `--grant-minutes`, for a stored question whose text, header or options no longer pass the check `ask` ran, and for confirmed words that name another amount or ask for less: ask again with the amount they want. "Another amount" (`lib/approval.mjs` grantRefusal) is any number but N, in any digits ("30", ".5", "30-45", "３０", "½"; Arabic-Indic, Devanagari and other non-Latin digits even when they mean N; fullwidth digits read as 0-9) or in words ("thirty", "one"); half, halves, quarter, third, couple, few, several, dozen, hundred, thousand, million, double, twice or triple; hours, seconds, days or weeks ("an hour", "90s", "1h"); "a minute"; or a total ("extend it to 60 minutes", "in total"). "Less" (confirmRefusal) is less, fewer, shorter, smaller, some, little, part, partly, partial, partially, portion, halfway or only ("Yes, only some of it"). The rules for `--confirm` are the ones above; without an approving answer it is refused. One answer is good for one `extend`.
- **A follow-on run:** `S/run.mjs init <new-run> … --continues <run>:<unit>` and add the unit under the same id, or under a new id with `add <new-run> <new-id> --continues <run>:<unit>`. Both runs record the link; the dashboard, unit page, maps and coordinator page show the chain with both ids, and `stats` counts it as one unit (rounds added up, outcome from the last run; a chain whose last unit was left open in a closed run counts as unfinished, neither passed nor stopped). A unit is continued once: a second follow-on of the same unit is refused, so continue the latest link instead. For a follow-on run made without the flag: `S/run.mjs link <new-run> <unit> --continues <run>:<unit>`.

**Status in the chat.** The person plans their next runs around this one, so say where it stands without being asked. Post `S/run.mjs status-line <run>` as one line, unchanged:
- at each milestone: a unit built, judged or merged, a question asked;
- at least every 30–45 minutes while agents run, even when nothing changed.

It reads "payday-x · Running: 2 of 4 units done (50%), building u3 round 2, about 1 h left (~21:40). Nothing needs you." When the run concludes (after `close`), post its closing line the same way: "payday-x concluded: done. Delivered: … Follow-ups: N in Gaps. Ready for the next run." (`references/hud.md`, Status word).

**Pit stops.** After a unit merges, a decision is recorded, or the run closes (after `close`), run `S/run.mjs push <run>` so the run is in the repo for another machine (`references/durability.md`). Never after every step. A push refused with "cannot tell whether the repo is public" names the file and the `"visibility"` key to set; `init` says the same while it is unset.

Briefs for agents outside a git worktree of this repo carry `COORDINATOR_DIR` from `S/run.mjs where`.

The run-level `decision` from `next`:

| Decision | Do |
|---|---|
| `split` | Add units, then `freeze`. |
| `continue` | Act on the units as above. |
| `integrate` | Send the integrator (it ends with `sub-skills/release-notes.md` when work merged), then `integrate pass|fail` (with `--gap` and `--cause` on a fail). |
| `done` | Finish (step 4) with outcome `done`. |
| `done-with-gaps` | Integration ran out of budget or hit the same gap twice. Finish with outcome `partial`, listing the gaps. When the last integration check failed and its fix then passed a fresh check of the fixed result, record that once with `integrate <run> pass --evidence "<the fix and the fresh check>"` (`guardrails.md`, Integration); the run is then `done`. |
| `stopped` | No unit passed. Finish with outcome `stopped`, listing each stop. |

**A question comes up mid-run?** If the recorded decisions answer it, follow them. If not and the step is reversible, take the safest choice that fits the decisions, log it with `S/run.mjs ask <run> --question "…" --header "<≤12 chars>" --option "<your choice>|<why>" --option "<other>|<what it means>" [--unit U]` (2–4 options, your choice first), and carry on: it shows in the HUD's Needs you box with its options and goes in the report for the person to confirm. Stop and ask only for an unapproved gated action, a finding that needs a design change, or a value question (`guardrails.md`, The lead's own checks), as in Asking below. A same-files question comes from `next` (`ask-person` above): ask it with `ask <run> --finish <unit>`, not a question of your own. Write it the step 1.7 way: the situation, why it matters, each option as a consequence, no run jargon.

### Asking

Every question after intake, mid-run and at the finish, is asked this way:

- **Only in two places:** the harness's question tool (AskUserQuestion in Claude Code), or the dashboards (the PC dashboard, the run's `serve` page and the hosted web one). Never as plain chat text, except the chat copy of dashboard-first mode below.
- **Log it first** with `S/run.mjs ask` (the options in the same order, your recommendation first). It prints `label` and `asking`.
- **The first line of the question is the `label`, as printed**, for example "payday · Financial Insights (payday-fi-1426) › Task u2: Payout summary card". Never type it yourself. The tool's header holds 12 characters, so put the short run name there.
- **`asking.mode` says how to ask.** Read it from the output; never guess. It is the run's intake answer (`note --kind decision --asking …`), else the project's `"asking"` in `.coordinator/coordinator.json` (`init.md`), else `dialog`.
  - **`dialog`** (the default): ask through the question tool. Record its answer with `S/run.mjs answer <run> qN --choice "<label>"` (or `--other "<their words>"`). In Claude Code the dialog holds this window until it is answered in the terminal, so an answer given first on a dashboard cannot close it.
  - **`dashboard`** (dashboard first): open no dialog. Write the question in the chat as plain text: the label on the first line, the question, then each option in order, your recommendation first and marked. Keep working on what does not depend on it. Act on the first answer: from a dashboard, heard through `watch`; or typed here, recorded with `S/run.mjs answer <run> qN --choice "<label>" --by person --confirm "<their words, verbatim>"`. Both places then show it.
- **Whichever answer comes first wins**; a later change, from either place, is honoured until you run `use-answer`. Act on the latest answer, then `use-answer`, so it can no longer change under you.

## 4. Finish

Do the actions approved at intake (for example, merge when the review is READY) and record each one (a merge also with `link <run> <unit> --merge <PR URL>`, then a critic with `references/sub-skills/verify.md` on the merged code).
