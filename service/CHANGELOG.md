# Changelog: Coordinator service

## Unreleased

- **Sync limits (c14):** syncs are queued: at most `SYNC_CONCURRENCY` (4) at once, `SYNC_PER_INSTALLATION` (2) per installation, taken in turn, and a push for a repo already queued joins it; a blob is fetched only when it fits `SYNC_BLOB_MB` (64) of blobs held at once. 200 signed pushes of 8 MB logs from one installation took the process to about 2 GB; now about 270 MB, another installation syncs in under 0.3 s and `/healthz` stays under 10 ms. Uninstalled ids are kept (migration 008, `uninstalled`), so a late `installation.created` is refused. `npm run sync -- <id>` stores an installation only after GitHub issues it a token. A forced re-read larger than `SYNC_MAX_MB` is kept in the database (`repos.reread`) and carried on by every later sync. Tests: `test/sync.test.mjs`.

- **Security review round 3 (c14):** webhook bodies in flight are capped per client address (5 MB, plus 1 MB of bodies declared 64 KB or less); the last 4 MB of the 32 MB budget is kept for those small bodies; a body must arrive within 10 s (408), and a cut, oversized or short body counts as a refused delivery for its address. Alert addresses are folded with NFKC and IDNA before the per-address confirmation count and before they are stored, as the SMTP envelope folds them. The 60-an-hour command cap counts only commands from people with push access; each commenter has 10 an hour of their own. Removing a repo from an installation deletes its alerts, sent and queued. Only `installation.created` makes an installation, so a late push or repository event after an uninstall brings nothing back. Tests: `test/edge.test.mjs`.

- **Security review for hosting (c14):** run logs, maps, lessons and `coordinator.json` are read in a worker thread with a 20 s limit (`src/parser.mjs`), and secret masking is linear, so one tenant's log can no longer freeze the server (it took 173 s on `'token_'` x 2000); log and write fields are clipped before masking. Confirming an alert email takes a button press on the page the link opens (a mail scanner's fetch confirms nothing), and at most 3 confirmation emails a day go to one person or one address; every alert and digest email carries a signed one-click stop link and RFC 8058 `List-Unsubscribe` / `List-Unsubscribe-Post` headers that work without sign-in. Uninstalling deletes the installation's alerts (sent and queued), subscriptions and audit rows too (one row records the removal) and closes its doorbell listeners; a test lists every table with an `installation_id`. The doorbell re-checks read access as the App when a stream opens and every 60 s. CSRF, OAuth state and doorbell signatures are compared as digests, so multibyte input is refused, never a 500. Webhooks: an address over the failure limit is answered before its body is read (unless the delivery names this App), all bodies read at once share a 32 MB budget, and a body seen before is skipped like a seen delivery id. Security-alert mentions are posted only on private repos; a push endpoint is never moved to another person; at most 60 comment commands an hour per installation; the Dockerfile pins `node:22-alpine` by digest; the manifest is `"public": true` for the hosted App (README: self-hosters may set it to false) and README says why it keeps `organization_projects: write`. Tests: `test/hostile.test.mjs` (the critic's proofs p1-p5).

- **Review round 2 (#12):** migration 006 starts `trail_seq_global` above every `trail_seq` already held (a database at 005); comment-command write tokens are narrowed to the state repo (`repository_ids`); alert recipients are re-checked as the App before every alert and digest (60 s cache), and someone who lost access is unsubscribed and sent nothing; a flagged "answer changed after use" note raises the alert; `/alerts` drops the snapshot chip and theme buttons and sends `frame-ancestors` only as a header; comment commands ignore indented code; each GitHub mention replaces the App's previous one for that person on the issue (README says why not the tracker comment); README's known limits cover the doorbell's use of `gh auth token`. New migration test (`test/migrations.test.mjs`, Postgres).

- **c12 merge:** the HUD's navigation links to `/alerts` for anyone signed in; the doorbell resolves its repo row by the id GitHub returns (`repoForPage(fullName, id)`); README's new "Known limits" says "a lead went quiet" is a guess from the pushed state; the end-to-end test has the lead beat after its push, so the HUD's answer is replayed by `pull` and used within one step.

- **c11 final-review follow-ups:** a trail refresh marks its run owed before it starts and clears the mark only after a clean finish, so a crash mid-refresh never loses an owed comment; `trail_seq` values come from one global sequence (`trail_seq_global`, migration 006; a counter in the memory store), so a run dropped and re-created cannot match a stale value; a repo page resolves to the row whose id GitHub's answer carries, so a stale same-named row in another installation no longer 404s the real page.

- **Answers and notes (#12):** answer and note forms on the run and unit pages, posting to `/run/<run>/answer|note` (Origin, CSRF, 30 a minute per person, push access re-checked with the person's token on every write; readers see the forms disabled with the reason). Comment commands `/coordinator answer qN …` and `/coordinator note …` on issues and PRs a unit of one open run links, for people with push access to the state repo: 👀 then 👍, or 😕 and a reason that quotes nothing. Each write is one commit on the state branch through the Git Data API, the same event `run.mjs` appends plus the rewritten snapshot and README, retried on a race and never forced; only the state branch, and only with the marker, is ever moved. App permissions: contents write, `issue_comment` events; tokens for commands are narrowed to contents (`SCOPES.write`). Migration 006 (`comment_commands`). Tests: writes, refusals, races, and an end-to-end run where the CLI lead asks, the HUD and a comment answer, and `pull` + `use-answer` use it.
- **Alerts (#12):** web push (VAPID), email (SMTP, a no-op when unset) and GitHub mentions for every trigger in design 9: a new question, a unit stopped, a run closed, a linked PR merged, checks red, a security alert, a lead gone quiet, an answer changed after use. Per-person settings on `/alerts` (repos, confirmed email, channels, time zone, quiet hours, question text opt-in), a quiet-hours digest, collapse of repeats within 15 minutes, minimal content by default, and the alerts sent with each channel's outcome. Migration `007_alerts.sql`; new settings `SMTP_*`, `VAPID_*`, `ALERT_SWEEP_SECONDS`, `DOORBELL_MAX_STREAMS`; dependencies `web-push` and `nodemailer`.
- **Doorbell (#12):** `POST /doorbell/token` (the person's GitHub token, checked for read access, swapped for a 15-minute token for one repo) and `GET /doorbell`, a Server-Sent Events stream that says only "run X changed" after each sync that changed it.

- **Security review fixes (round 6):** every trail refresh of a repo's runs, from a sync or from a merge or check webhook, now runs in that repo's one serial queue, so two never overlap and the last to finish can no longer wipe a deferral the other recorded. A refresh that owes a write marks the run and bumps a counter (`trail_seq`, migration 005); a clean refresh clears `trail_pending` only if the counter still holds what it read first, so a deferral recorded meanwhile (another process on the same database) survives. A link now resolves to the run's own installation's repo row (`db.repoByName(installationId, name)`), never a same-named row from another installation; the page lookup by URL is `db.repoForPage`.
- **Security review fixes (round 5):** a trail refresh started by a merge or check webhook now sets `trail_pending` when a comment is held back by the write cap or the refresh fails partway (a GitHub 5xx), the same rule a sync uses; the next periodic resync lands the merge or checks line by editing the comment, never posting a second. A failed refresh during a sync is now flagged too.
- **Security review fixes (round 4):** links per unit are capped at ingest (the trail's 10, one constant), and a page view checks the viewer's access only for linked repos that have GitHub events, at most 20 of them (one hostile log no longer makes thousands of GitHub calls on a viewer's token). A comment held back by the write cap marks its run `trail_pending` (migration 004); every later sync retries it even when the branch tip has not moved, and a restart keeps the flag without posting twice. Webhooks with a Content-Length over 5 MB are refused before the body is read; `MAX_CONNECTIONS` (default 1000) and a 30 s request timeout bound the server; the tracker skips null entries in `rounds`.
- **Security review fixes (round 3):** the webhook signature is always checked first and a verified delivery is never rate limited (refused deliveries from GitHub's shared addresses could block real ones); a periodic resync of every installation (`RESYNC_MINUTES`, default 15) heals missed deliveries. The tracker template checks every number (`maxRounds`, scores) and drops anything but id characters from the marker. The consent check is cached for at most 60 s; runs over 50 units are refused, at most 10 links per unit are written, and comment writes are capped per installation.
- **Security review fixes (round 2):** tracker comments and board writes are fenced to the run's project (the state repo, plus linked repos listed in `coordinator.json` `repos` whose own default branch names the state repo as `primary`); links outside it are read-only. Run text in tracker comments is in code spans (no autolinks, mentions or markup). Deeply nested lessons, `coordinator.json` or state no longer crash a sync; the repo records why. `ACCESS_TTL_SECONDS` capped at 60; PKCE and a fresh session on every sign-in; signed webhooks are never rate limited; unknown repos get the same GitHub check as unreadable ones. The HTTP, access and webhook tests run against Postgres too (a throwaway schema per app) when `TEST_DATABASE_URL` is set.
- **The GitHub trail (#11):** one tracker comment per unit on each linked issue or PR (the skill's `lib/tracker.mjs` template), edited in place, never re-sent unchanged, re-made when deleted, and status only outside the run's own private repo; board fields Run and Unit state (and the board's Status, when mapped) on an organisation board named in `coordinator.json`; `pull_request` and `check_suite` webhooks stored against the PR, shown in run and unit timelines to viewers who can read that repo, and refreshing the trail. Tokens narrowed per job; App permissions: issues and pull requests write, checks read, organisation projects write; contents stays read.
- **Project map** on the web (`/run/<run>/map`), from the pushed `runs/<run>/map/events.jsonl`, replayed and checked with the skill's `lib/map/log.mjs` (new `fromText`); linked from the header next to Maps; a bad log keeps the last good map.
- **Maps** on the web: `/r/<owner>/<repo>/run/<run>/maps`, from the skill's maps page. A `REPO_PAGES` hook for more repo pages (the project map).
- The Needs-you box says to answer in the chat for now; evidence files show as "file kept locally" instead of links.
- **First release (#11): GitHub App and read-only web dashboard.** Webhook ingest of the `coordinator-state` branch (signature checked, deliveries de-duplicated, unchanged tips and logs not read again, every log validated with the skill's event schema and masked again), a Postgres read model (in memory without `DATABASE_URL`), sign-in through the App's user authorisation, a per-request read-permission check with GitHub (cached per person for 60 s; no access is a 404), and the projects, runs, run, unit and coordinator pages drawn by the skill's own renderers. Manual sync from a repo page or `npm run sync`. Dockerfile, docker compose for local Postgres, App manifest and Dokploy notes in the README. AGPL-3.0.
